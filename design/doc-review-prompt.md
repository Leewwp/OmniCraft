## 提示词正文

你是一位资深全栈架构师，擅长交叉校验产品需求文档、技术架构、任务列表和 UI 设计文档之间的一致性。请基于以下项目文档，完成全面校验。

### 项目背景

OmniCraft（万象工坊）是一个创意内容社区平台，支持二创（同人作品）和原创内容的发布、浏览、协作。

**技术栈：**
- 前端：Next.js 15 (App Router) + TypeScript + Tailwind CSS + shadcn/ui + next-intl (i18n)
- 后端：Go (Gin + GORM) + PostgreSQL (pgvector) + Redis
- 客户端：Tauri (Rust + WebView)
- 存储：Aliyun OSS
- AI：SSE 流式（禁用 WebSocket），Agent 工具调用模式

**核心特性（均受 Feature Flag 控制）：**
- IP 管理 + 二创/原创内容发布（含 PR 协作）
- AI Agent（上传辅助、合规检测、语义搜索、使用指导、智能聊天）
- 网络判官系统（资质考试 + 投票裁决 + 理由投票）
- 信誉分体系 + 素质建设课程
- 创作者支持（打赏码/外部链接，无资金流闭环）
- 讨论区、通知、私信、浏览历史

### 校验任务

请完成以下 8 项校验，逐项输出结果：

#### 1. 跨文档一致性
- PRD 定义的每项功能是否在 architecture.md 有对应的技术实现设计（API、DB Schema、配置项）
- architecture.md 的 DB Schema（§4）字段类型、枚举值、索引是否与 PRD 业务规则匹配
- Feature Flag 名称和默认值在 PRD、architecture.md、CLAUDE.md 中是否一致
- 分类枚举（IP 分类、内容类型、原创区大类）在 architecture.md §10、task.json、UI Design.md 中是否一致

#### 2. CLAUDE.md 编码规范校验
- 编码标准是否与 architecture.md 的技术选型匹配（Go 版本、包管理、目录结构）
- Agent 工具白名单是否覆盖 task.json 中所有 Agent 相关任务的操作
- 安全规则（bcrypt、参数化查询、HTTPS、CSP）是否与 architecture.md 安全章节一致
- 业务规则速查表是否与 PRD 中的数值（信誉分阈值、PR 超时时间、文件大小限制等）一致

#### 3. task.json 覆盖率校验
- PRD 中定义的每项用户可感知功能是否有对应的 task.json 任务
- 每个任务的 steps 是否足够具体，能否直接指导开发（无歧义）
- 任务间的 `depends_on` 依赖链是否正确（无循环依赖、无遗漏前置依赖）
- 检查是否存在"低 ID 任务依赖高 ID 任务但缺少 depends_on"的情况
- 新增的 Task 84（用户主页）和 Task 85（浏览历史）是否完整覆盖 UI Design.md 对应页面定义

#### 4. progress.txt 一致性
- progress.txt 中标记完成的任务是否与 task.json 中 `passes: true` 的任务一致
- 是否有 task.json 中已标记完成但 progress.txt 未记录的任务（或反之）

#### 5. UI Design.md 完整性
- UI Design.md 中每个页面（P01-Pxx）是否都有对应的 task.json 任务
- task.json 中每个前端任务的 `ui_spec_ref` 引用的章节是否在 UI Design.md 中存在
- 页面间的跳转路由是否一致（如用户主页 → 设置页、内容详情 → 用户主页等）
- 响应式断点（移动 ≤ 700px / 平板 ≤ 1100px / PC > 1100px）在所有文件中是否一致
- 设计系统的 Token（颜色、字体、间距）是否与 CLAUDE.md 或 architecture.md 的约定一致

#### 6. 交互设计合理性
- 是否存在违反常见人机交互原则的设计（如缺少加载状态、缺少错误反馈、缺少空状态）
- 关键操作（删除、注销、发布）是否有二次确认
- 信息架构是否合理（导航层级、页面分组）
- 移动端适配是否有遗漏（表格横滚、侧边栏收起等）

#### 7. 数据库 Schema 深度校验
- 所有表是否有合适的索引（高频查询字段）
- 外键关系是否完整（CASCADE/SET NULL 策略是否合理）
- JSONB 字段是否有文档化的结构约定
- 枚举值是否在应用层有校验（CHECK 约束或 GORM Validate Tag）
- 迁移编号是否连续、无冲突（Task 63 的 023-029，Task 75 的后续编号，Task 85 的 030）

#### 8. 优化建议（可选）
- 是否有可以合并或简化的任务
- 是否有过度设计（MVP 阶段不需要的复杂度）
- 是否有遗漏的非功能性需求（性能、可观测性、备份策略）

### 输出要求

1. **逐模块输出**：按上述 8 个校验项分模块列出结果
2. **标注来源**：每个问题标注涉及的文件名和具体章节/行号/Task ID
3. **已修复过滤**：对照 `docs edited history.md`，**不要重复报告已修复的问题**
4. **严重程度分级**：
   - 🔴 **阻塞**：矛盾会导致开发错误或运行时 Bug
   - 🟡 **警告**：不一致但不影响功能，建议修复
   - 🟢 **建议**：优化建议，可延后处理
5. **修复建议**：每个问题给出明确的修复方案（修改哪个文件的哪个部分，改成什么）
6. **最终结论**：如果无阻塞问题，给出"所有文档一致、无矛盾、无遗漏，可进入下一步开发"的明确结论
