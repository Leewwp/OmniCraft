## 0. 目标与定位

为 A-04（#286）四配置消融与 #204 面试证据链提供**有规模说服力的数据底座**：万级合成语料（本地）+ 冻结 golden set（150–200 条）。生产演示种子（2k–5k）为人工执行清单，不属 idle goal。

## 1. 语料生成矩阵（独立会话执行，产出为纯文本，不入库）

## 2. 注入方案（分层）

### 2.1 本地全量（万级）——REST API 注入

- 虚拟作者 token 经真实 REST API 发布；**禁止直写数据库**（绕过发布事件 = 索引永不更新，是最糟状态）。
- 走完整真实管线：表单校验 → 审核门 → 发布事件 → Outbox → Worker → chunk + embed → pgvector/关键词索引。
- 脚本要求：限流（如 2–5 rps）、断点续跑（幂等，记录已注入 content_id）、错误率阈值熔断（如 >2% 停止）、管理员审核流转步骤（种子内容走真实审核，不建白名单免审）。
- 注入后按 AGENTS Step 2 核查 worker lag=0。

### 2.2 本地小子集——Playwright UI 注入（Agent 扮演真实用户）

- 20–50 条内容 + 若干评论/讨论/收藏/关注，经浏览器表单完成。
- 作用：主流程 E2E 验证（发布→审核→展示→检索）+ 演示素材/截图。评论不入检索索引（已裁决），仅作站点活性。

### 2.3 生产种子（2k–5k 精选）——人工执行清单（不属 idle goal）

1. 等当前总序发出一个稳定 release；`pg_dump` 备份并归档（沿用 ops 纪律）。
2. 低峰窗口，同一注入脚本指向生产 HTTPS API，限速 1–2 rps。
3. 前后健康检查：`/healthz`、backend P95、postgres 容器内存、worker lag。
4. 完成后归档站点截图进 #204 证据链。
- 口径红线：种子数据永远是"种子数据"，任何材料不出现用户量/DAU/运营数据表述。

## 3. Golden Set（150–200 条，四分层）

配比：精确 40% / 语义 30% / 可见性 15% / 无答案 15%；**必须包含 #290 交付的 IP 内搜索分层用例**（问题限定在某 IP 范围内检索）。

流程：AI 初标（问题 + 期望内容集合 + 出题理由）→ 用户逐条复核 → checksum 冻结 → 修改需升版本。

## 4. 标注规则 v0.9（待用户确认后定稿）

1. **条目结构**：1 条 case = `{问题, 期望内容集合（1..n 个 content_id）, 分层, 出题理由}`。
2. **允许多正确答案**：问题主题若有多篇匹配，全部标入期望集合，不追唯一最优（符合检索现实）。
3. **期望内容必须是答案主体所在**（正文包含答案）；仅顺带提及不算。
4. **精确类**：问题必须包含标题原文或专有名词，不得含糊。
5. **语义类**：问题禁止复用标题用词（同义改写，人为制造词汇鸿沟），否则测不出语义召回。
6. **可见性类**：期望集合标注为"不得出现"（如仅粉丝可见内容在陌生读者查询下泄漏 = 失败）。
7. **无答案类**：必须先经全语料检索确认确实无答案，才可冻结。
8. 每条必带一句出题理由；用户复核只判断"配对合理性"，不需要理解检索算法。

评测判定（脚本执行）：Recall@10（期望集合任一出现在 Top-10）为主指标，辅以 MRR；可见性类看泄漏数（目标 0）；无答案类看 Top-10 相关率（目标 0）或拒答。

## 附录 A：Tika 调研结论（Phase 2 备选，本轮不实现）

Apache Tika：JVM 容器化文档解析服务（tika-server），REST 接口（PUT 文件 → 纯文本 + 元数据），支持 PDF/Office 全家/OCR 等 1000+ 格式；Elasticsearch ingest-attachment 内嵌即 Tika。适配 Go 架构：一个 HTTP 客户端函数 + 解析结果转统一 chunk 模型，零 SDK、零 Python 依赖，约 1–2 天。服务器影响：常驻 256–512 MB（JVM），大 PDF 解析有峰值——对 3.6 GiB lean 主机是显著新增，故列 Phase 2（升配后常驻，或上传时短时拉起）。启用前提：附件上传成为产品功能。
